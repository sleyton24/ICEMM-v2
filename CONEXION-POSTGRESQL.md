# Conexión a PostgreSQL — Diseño y Plan

> Generado por análisis multiagente (2026-06-10). Diseño para conectar el monolito (hoy 100% localStorage) a un backend PostgreSQL. Basado en [ARQUITECTURA-DATOS.md](ARQUITECTURA-DATOS.md).

## 1. Recomendación de arquitectura

> **DECISIÓN DEL USUARIO (2026-06-10):** el monolito se despliega en el **VPS existente (187.127.29.98)** junto a la app ICEMM y se conecta a la **MISMA base PostgreSQL que ya usa la app de la carpeta `ICEMM/`**. NO se monta infra nueva ni backend nuevo: se **EXTIENDE** el backend/DB de ICEMM con las tablas del monolito. (El "servidor que ya no se ocupa" era el SQL Server del ERP PRESTO, cuya clave está vencida — NO el VPS de ICEMM.) La carpeta `ICEMM/` (incl. `icemm~/`) se conserva como respaldo. → Aplica la **Opción A** de abajo, sobre la infra existente (sin el redeploy en infra nueva que se mencionaba como hipótesis).

RECOMENDACION: reusar el backend ICEMM (Node/Express/Prisma/PostgreSQL) como base y EXTENDERLO con las tablas del monolito, NO montar un backend nuevo. (Confirmado por la decisión del usuario: se usa el VPS y la base existentes de ICEMM.)

== OPCION A — Reusar/extender el backend ICEMM (RECOMENDADA) ==
El repo ICEMM/backend ya trae todo lo costoso de levantar: Express + helmet + CORS por lista blanca + rate-limit (login 10/15min, general 200/min), JWT con fail-fast si JWT_SECRET es placeholder o <32 chars, bcrypt, middleware authMiddleware/softAuth/requireRole, BETA_MODE para QA, Prisma con singleton, /health con SELECT 1, validación Zod por ruta, y un patrón DTO ya probado (toProyectoDTO mapea filas Prisma a la forma exacta que consume el front). El modelo de roles admin/editor/viewer/director y el M2M UserProject (visibilidad por proyecto) calzan con budget-control:users del monolito. La correspondencia de dominio ya está resuelta: Project.unidadNegocioCodigo (Int) == unCode (string '02'), Project.cutoffMesReal ("YYYY-MM") == el controlMonth que hoy el monolito reinventa por heurística en cada módulo, y CargaERP ya guarda gasto real en UF por centro de costo y mes. Pros: mínimo time-to-first-byte, seguridad ya endurecida (no la rehago), un solo modelo de auth/usuarios para los dos frontends (la app itemizada de ICEMM y el monolito de gestión), Prisma da migraciones versionadas (reemplaza el frágil migrateSchema v1->v2 del cliente). Contras: el schema Prisma de ICEMM está orientado a "proyecto itemizado con slots", no a "presupuesto/actuals/cashflow por año"; hay que AGREGAR tablas (no calzan 1:1, ver tablas) y aceptar que conviven dos paradigmas en un mismo Postgres. Mitiga: tablas nuevas con prefijo claro y FKs a Project; no toco las de ICEMM.

== OPCION B — Backend nuevo dedicado al monolito ==
Servicio Node/Express/Prisma nuevo, schema limpio diseñado desde cero para budget-control:*. Pros: schema coherente sin arrastrar el modelo de slots; libertad de diseño; despliegue independiente. Contras: reescribir auth/seguridad/rate-limit/DTOs que ICEMM ya tiene endurecidos (semanas, y es donde se cometen los bugs de seguridad); DOS catálogos de usuarios y de proyectos que se desincronizan (el unCode/unidadNegocioCodigo viviría duplicado); dos despliegues y dos puntos de monitoreo. Solo se justifica si la empresa quiere aislar por completo gestión de itemizado.

== CASO "el VPS de ICEMM ya no se ocupa" (transversal a A y B) ==
"No se ocupa el servidor" != "no sirve el código". Recomiendo: tomar el REPO ICEMM/backend (Opción A) y RE-DESPLEGARLO en infraestructura nueva, NO resucitar el VPS viejo (IP 187.127.29.98 que aparece hoy hardcodeada como cc-url y en el iframe HTTP plano del módulo ControlCostos). Stack objetivo sugerido: Postgres administrado (Neon/Supabase/RDS o un Postgres en el mismo VPS nuevo) + el backend en un contenedor (Docker) detrás de Nginx con TLS (Let's Encrypt). El monolito hoy es un .html servido como archivo; pasa a servirse desto detrás del MISMO origen que /api (evita líos de CORS y permite cookie httpOnly en vez de JWT en localStorage). Concretamente: dejar CORS_ORIGIN al dominio real, generar JWT_SECRET nuevo (32+ bytes), BETA_MODE=false en prod, correr `prisma migrate deploy`, y matar la IP plana del iframe (servir Presto/ICEMM por HTTPS o embeber por API). Si el VPS viejo está realmente muerto, no hay datos que rescatar de él para el monolito: la verdad del monolito está hoy 100% en el localStorage de los navegadores de los usuarios, así que el "dato a migrar" es el export JSON del catálogo budget-control:* de cada navegador (existe collectAllData/export), no el contenido del VPS. CONCLUSION: Opción A (reusar repo) + redeploy en infra nueva. Esfuerzo neto vs B: ~40-50% menos por reutilizar seguridad, auth y patrón DTO.

## 2. Reuso del backend ICEMM existente

Mapeo de lo YA existente en ICEMM a datos del monolito (reusar tal cual o como ancla de FK):

- Project (id, nombre, unidadNegocioCodigo Int?, cutoffMesReal "YYYY-MM") -> ANCLA del catálogo budget-control:projects. unidadNegocioCodigo ES el unCode (parsear '02'->2 y formatear 2->'02' en el DTO). cutoffMesReal ES el controlMonth canónico que hoy se reinventa por heurística en 8 módulos: al conectar, el monolito debe LEER el controlMonth de aquí en vez de derivarlo de actuals. Reuso: la fila Project se reusa como padre; los campos ricos del monolito (contractType, status, isOffBudget, fechas, curvas S, budgetByCategory 8 cats, contract.*, replacesProject) NO caben en Project y van a una tabla nueva ProjectGestion 1:1 (ver tablas). Endpoints GET/POST/PATCH/DELETE /api/projects se reusan; se extiende el DTO.

- CargaERP (agregadoPorCcosto, agregadoPorCcostoPorMes, transaccionesPorCcosto, totalUF, unidadNegocioCodigo, mesesDisponibles, todo en UF) -> es el GASTO REAL ERP por centro de costo y mes. Cubre el MISMO dominio que budget-control:actuals:{year}:{mm}.rows (real itemizado clasificado por unCode/concepto/total en UF). NO calza 1:1 en granularidad: CargaERP es 1 por proyecto (projectId @unique) sin dimensión año-mes en clave ni clasificacion de categoría de costo del monolito. Decisión: NO forzar actuals dentro de CargaERP; crear tabla nueva Actuals indexada por (unCode, year, month) con las rows clasificadas. Donde SI se reusa CargaERP: si en el futuro el ERP carga por la app itemizada de ICEMM, un job puede derivar Actuals desde CargaERP.agregadoPorCcostoPorMes. Por ahora: CargaERP queda como está; Actuals es la fuente del monolito.

- PlanCuentas (familias FamiliaMacro[] + 188 cuentas CuentaCosto[], plan activo marcado) -> es la fuente del MAPA DE CLASIFICACION (classifyManagerCode / COST_CATS 600/700/800). Reuso: GET /api/plan-cuentas ya devuelve el plan activo; el monolito debe leer de aquí la tabla de clasificación en vez de tenerla hardcodeada/duplicada en :2500-2513 (esto unifica la fuente que hoy está triplicada monolito vs src/lib). OJO: el mapeo está BLOQUEADO en revisión con contabilidad — no cambio el mapeo, solo lo centralizo aquí cuando contabilidad lo apruebe.

- Informe (snapshot inmutable por proyecto, numero auto-incremental, snapshotProyecto Json, aprobadoPor, fechaAprobacion) -> patrón IDENTICO al cierre del monolito (cierre:{year}:{mm} con modulos.* congelados). Reuso CONCEPTUAL del patrón (snapshot Json inmutable + autor + numero + aprobado), pero la granularidad difiere: Informe es por proyecto; el cierre del monolito es por (year, mes) consolidando 7 módulos de TODA la cartera. Creo tabla nueva Cierre con la misma filosofía (snapshot Json inmutable, cerradoPor, schemaVersion). Informe de ICEMM se reusa tal cual para sus propios snapshots itemizados.

- User + UserProject + auth (JWT, bcrypt, requireRole, BETA_MODE) -> reemplaza budget-control:users y budget-control:session COMPLETO. El monolito hoy guarda passHash en localStorage (inseguro); pasa a /api/auth/login (bcrypt server-side) + JWT. UserProject (visibilidad por proyecto) habilita el tenant/RBAC que el monolito NO tiene. Reuso total de /api/auth y /api/users; el módulo Usuarios del monolito pasa a ser un cliente de /api/users.

- Comentario (por projectId + codigoPartida) -> no tiene equivalente directo en el monolito hoy; queda disponible para anotaciones futuras. No se reusa para datos del monolito.

NO existe en ICEMM (todo nuevo): budget anual por categoria, cashflow, control-obras, plazo-curvas, overrides, proj-completion, proj-snapshot, los 4 *-snapshot vivos de módulo, mayor:latest, balance:latest, uf-table, config global, saved-reports.

## 5. Capa `dataStore` async (abstracción de persistencia)

OBJETIVO: introducir una abstraccion async dataStore que HOY siga sobre localStorage y MAÑANA pegue al API, sin reescribir los 151 call sites de storage.get/set. Es la pieza mas importante para "preparar" la conexion. Diseño en 4 capas.

== 1. dataStore con la MISMA superficie que `storage`, pero async ==
Hoy: `const x = storage.get('budget-control:cashflow:'+year)` (sincrono) y `storage.set(key, value)`. Estrategia: introducir un objeto `ds` con `await ds.get(key)` / `await ds.set(key,value)` y un `backend` intercambiable: LocalBackend (envuelve el storage actual, resuelve la promesa de inmediato) y ApiBackend (mapea key->endpoint con fetch). NO se elimina `storage`; LocalBackend lo reusa, conservando deteccion de corrupcion (.corrupt), notifyStorageError y reportCriticalSaveFailure. El FLAG de cual backend usar vive en window (`window.ICEMM_BACKEND='local'|'api'`) para poder activar el API sin tocar codigo de modulos.

== 2. Migracion de call sites sin reescribir 151 a mano: hidratacion + cache sincrono ==
El monolito es React-via-Babel y muchos get son sincronos dentro de render/useMemo: convertir cada uno a await es inviable y arriesgado. Solucion: un CACHE EN MEMORIA hidratado al arranque (snapshotCache: Map<key,value>). Fase de bootstrap async (antes del primer render util) que precarga del backend TODAS las claves del año/contexto activo (projects, budget:{year}, actuals del año, cashflow:{year}, overrides, proj-*, control-obras, plazo-curvas, config, lista-cierres). Luego `storage.get(key)` se redefine para leer del snapshotCache (sigue SINCRONO -> los 151 call sites no cambian de firma); `storage.set(key,value)` escribe en snapshotCache Y encola una mutacion async (write-behind). Asi el monolito sigue "sincrono por dentro" y la red queda detras de la cola. Las claves no precargadas (un año no abierto) disparan un fetch lazy + re-render del modulo que las pidio (patron suspense manual: get devuelve el cache o null y dispara carga). Esto acota el cambio a ~la definicion de storage + un bootstrap, no a 151 sitios.

== 3. Mapeo key -> endpoint (router de claves) ==
ApiBackend traduce el namespace budget-control:* a REST con un tabla de ruteo declarativa (resuelve la ausencia de KEY_REGISTRY que hoy es un gap): `projects`->/api/projects; `budget:{y}`->/api/budget-annual/{y}; `actuals:{y}:{mm}`->/api/actuals/{y}/{mm}; `mayor|balance:latest`->/api/erp-source/{tipo}/{y}/{m} (el router INYECTA el periodo activo, eliminando el bug de 'latest' global); `cashflow:{y}`->/api/cashflow/{y}; `overrides|proj-completion|proj-snapshot:{y}`; `control-obras|plazo-curvas:{y}`; `{modulo}-snapshot:{y}`->/api/module-snapshot/{modulo}/{y}; `cierre:{y}:{mm}`->/api/cierres/{y}/{mm}; `lista-cierres|ultimo-cierre:{y}` se DERIVAN de GET /api/cierres/{y} (no son claves propias en DB); `saved-reports:{y}`; `config|cc-url|schema-version`->/api/config; `users|session`->/api/users + /api/auth. El registry es la unica fuente de verdad de "que clave existe y su forma" (hoy se descubren por prefijo en runtime).

== 4. Caché offline + cola de sync + concurrencia para cierres ==
- OFFLINE/CACHE: snapshotCache persiste a localStorage como respaldo (la app sigue leyendo si el API cae). El backend LocalBackend NUNCA se borra: en modo API, localStorage pasa a ser cache de lectura, no la verdad.
- COLA DE SYNC (write-behind): cada ds.set encola {key,value,ts,opId} en una outbox persistida en localStorage. Un worker la drena contra el API (PUT idempotente). Si falla: reintento con backoff; el banner StorageErrorBanner ya existe para avisar. reportCriticalSaveFailure pasa a significar "no se pudo encolar" (raro) o "el server rechazo" (conflicto). Idempotencia: PUT por (key) con last-writer-wins para datos de un solo dueño; para datos compartidos usar concurrencia optimista.
- CONCURRENCIA OPTIMISTA: cada recurso lleva `updatedAt`/`version`; ds.set envia If-Match (ETag/version). 409 -> el modulo re-hidrata y avisa "otro usuario cambio esto". Esto reemplaza el last-write-wins global por navegador (bloqueante estructural actual). Critico para saved-reports (3 modulos al mismo array), control-obras (blob anual), budget autosave (keystroke).
- CIERRE = TRANSACCION SERVER-SIDE: el cierre deja de ser multi-clave en el cliente. ds llama POST /api/cierres/{y}/{mm}; el server, en UNA transaccion Postgres, lee los snapshots vivos (o los exige), congela Cierre (con cerradoPor+schemaVersion), y marca el periodo cerrado. Atomico: o se cierra todo o nada (corrige el cierre parcial de :7745-7770). El server RECHAZA escrituras posteriores a meses cerrados (lo que el front hoy intenta y a veces no logra, ej. PlazoCurvaPanel). Lock por (year,mes) para evitar doble cierre concurrente.
- DEBOUNCE: autosave de budget/proyecciones se debouncea en la cola (coalescing por key) para no martillar el API en cada keystroke.

## 7. Riesgos

- Los 151 call sites de storage.get son SINCRONOS dentro de render/useMemo. Forzar await en cada uno rompe el monolito. El cache-en-memoria + hidratacion async (capaDataStore paso 3/7) es la unica via segura; si una clave no esta precargada, un get devuelve null transitorio y puede mostrar 0/— hasta que llegue el fetch. Riesgo de cifras erroneas momentaneas si la hidratacion no cubre todo el contexto del año visto.
- Snapshots derivados (proj-snapshot y los 4 *-snapshot) dependen de que el navegador RENDERICE la pestaña para existir. Al pasar al server, si el cierre exige esos snapshots y nadie abrio la pestaña, el cierre falla o congela null. Hay que regenerarlos server-side o forzar su calculo antes de cerrar; mover ese calculo al server es trabajo extra no trivial (la logica esta inline en el monolito, no en src/lib salvo flujocaja).
- Las claves 'latest' de mayor/balance NO llevan año: al normalizarlas a (tipo,year,month) en DB, hay que decidir a que periodo pertenece cada carga historica importada. El import (paso 8) puede mapear mal periodos viejos y el Check Contable daria falsos descuadres.
- unCode no esta validado/normalizado fuera del form (import/sample/migrateSchema). Si la DB impone UNIQUE/Int sobre unidadNegocioCodigo, el import de datos historicos puede fallar o colisionar (proyectos con unCode duplicado o sin padStart). Necesita una pasada de saneamiento antes de POST /api/sync/import.
- Concurrencia: pasar de last-write-wins por navegador a optimista (If-Match) cambia el comportamiento percibido. Usuarios acostumbrados a 'guardo y listo' veran 409 'otro usuario cambio esto'. Riesgo de friccion y de perder cambios si el merge no esta bien definido, sobre todo en saved-reports (3 modulos al mismo recurso) y control-obras (blob anual).
- El cierre transaccional server-side reescribe una mecanica central (:7745-7770). Bug aqui = no se puede cerrar el mes (bloquea al directorio) o se cierra inconsistente. Requiere tests de la transaccion y un camino de reversion (hoy el monolito ni guarda autor del cierre).
- El mapeo de clasificacion 600/700/800 esta BLOQUEADO en revision con contabilidad. Centralizarlo en PlanCuentas antes de que se apruebe arriesga congelar un mapeo que va a cambiar. Mantener la lectura preparada pero NO migrar la fuente hasta el OK.
- La logica de dominio (EBITDA, proyeccion por curva, margen a termino) esta duplicada/triplicada inline en varios modulos y NO usa src/lib. Si el server empieza a calcular (ej. clasificacion en /actuals/load, arrastre en /cashflow), aparece una CUARTA copia de la formula; cualquier divergencia front/back produce cifras que no cuadran. Hay que unificar en src/lib y compartirla (mismo paquete) o el server queda como mera persistencia y todo el calculo sigue en el front.
- Modelo multi-tenant: hoy todo es global por navegador (sin tenant). UserProject de ICEMM da visibilidad por proyecto pero NO segmenta datos anuales (budget/cashflow/cierre son de cartera, no de un proyecto). Si la app debe servir a mas de una empresa/constructora, falta una dimension tenant que ninguna tabla (ni ICEMM ni las nuevas) tiene hoy.
- El iframe de ControlCostos (IP 187.127.29.98, HTTP plano, sandbox allow-same-origin+allow-scripts, URL validada solo con trim que acepta javascript:) es un hueco de seguridad y ademas crea DOS silos (Postgres del iframe vs actuals en localStorage) que pueden divergir. Conectar el monolito a Postgres no resuelve esto solo; hay que reemplazar el iframe por consumo via API.
- Tamaño de payloads: actuals.rows y los Json de CargaERP/transaccionesPorCcosto pueden ser grandes (el backend ya sube limit a 50mb). Hidratar todo el año al bootstrap puede ser pesado; necesita paginacion/carga selectiva por modulo o el arranque se vuelve lento.
